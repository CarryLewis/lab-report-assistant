# 试点与验证设计

## 试点目的

试点的目的是验证产品是否帮助教师完成批改，而不是证明 AI 能独立给分。首轮只选择一门课程、一个 Lab Report 类型、一个 rubric 和少量愿意参与的教师。

## 试点准备

试点开始前应完成：

1. 选定作业题目和本次使用的 rubric 版本。
2. 准备少量适合测试的历史报告，并确认可用范围。
3. 选择代表好、中、差表现的报告，涵盖常见问题。
4. 请课程教师说明他们原有的批改步骤、常见扣分点和正式反馈习惯。
5. 明确系统只提供辅助建议，最终成绩仍由教师决定。

## 验证方法

先让系统分析已经有教师批改结果的历史报告，再由教师查看系统输出。教师需要重点判断：

- 报告结构是否正确反映学生的写作主线；
- 原文证据是否定位正确；
- rubric 建议是否有帮助；
- 系统是否遗漏关键问题或制造了错误问题；
- 输出是否减少了阅读和整理反馈的时间。

不要只记录总体“好用/不好用”。每个问题都应归类为解析、证据、rubric、科学理解、语言表达或交互流程问题。

## 建议观察的指标

- 可成功解析的报告比例；
- 建议具有可定位证据的比例；
- 教师接受、编辑、拒绝建议的比例；
- 教师完成一份报告所需时间的变化；
- 教师对输出可理解性和可信度的评价；
- 解析失败、证据错误和高风险误判的具体案例。

这些指标用于改进，不用于将教师专业判断简化为单一分数。

## 扩大试点的条件

在以下条件基本满足后，才考虑增加课程或教师：

- 教师能独立完成完整工作流；
- 大多数建议有清晰且正确的证据定位；
- 教师认为结构与 rubric 视图确实节省时间；
- 已知错误类型有明确处理方式；
- 课程负责人认可数据范围与实际使用方式。

若上述条件不满足，应继续缩小问题范围并改善当前试点，而不是直接增加模型、功能或使用人数。
